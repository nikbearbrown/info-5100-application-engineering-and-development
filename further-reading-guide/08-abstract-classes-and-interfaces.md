## Further Reading — Module 8: Abstract Classes and Interfaces

> **Content note:** Despite the title "Abstract Classes and Interfaces," this chapter covers file persistence, CSV I/O, the CRUD data lifecycle under persistence, IOException handling, and save-strategy trade-offs. This guide addresses the actual chapter content.

The chapter introduces persistence at exactly the moment it becomes unavoidable — when an in-memory catalog vanishes on restart — and then stops before answering several questions the code raises but does not resolve. Why does `BufferedReader` live inside `FileReader`? What happens when both the body of a `try` block and the `close()` call throw exceptions at the same time? What does "atomic rename" actually mean at the operating system level, and why does it prevent the half-written file problem? These are not edge cases; they are the failure modes that will surface the moment a project is tested under realistic conditions. The question of how far flat-file persistence can take a system — and where it breaks down — is still actively debated in software architecture, and the chapter's save-strategy table is a miniature version of a much larger decision space.

Read the Key resource before attempting Exercise 3 (writing explicit exception handlers) or Exercise 7 (the dirty-flag design challenge). Choose one Recommended resource based on which concept felt least resolved: pick Bloch's Item 9 if the manual `close()` calls in the chapter's examples left you uncertain about what happens when both the write and the close fail simultaneously, or pick the Oracle try-with-resources tutorial if you want a quick concrete demonstration of the syntax fix. The Further resource is genuinely optional — set it aside unless you want to understand why databases exist and what exactly they replace.

### Key

**The Java Tutorials: Basic I/O** — Oracle, 2023 | https://docs.oracle.com/javase/tutorial/essential/io/

The Oracle Java Tutorials "Basic I/O" section is the authoritative introductory reference for the `java.io` class hierarchy that carries this chapter's entire persistence layer. It covers `BufferedReader`, `BufferedWriter`, `FileReader`, `FileWriter`, and the `IOException` subclass tree — specifically `FileNotFoundException`, `EOFException`, and `IOException` itself — in a single navigable structure that makes clear which exception corresponds to which failure mode. I included this because the chapter uses these classes throughout but introduces none of them as a hierarchy; students who have not read this resource tend to write catch blocks that catch `Exception` at the root and swallow everything silently, which is exactly the failure pattern the chapter warns against. Focus on the "Reading, Writing, and Creating Files" section and the `IOException` subclass overview; budget 15–20 minutes for a first read. Before writing the exception handlers in Exercise 3, confirm which specific subclass maps to "file not found at startup" — catching `FileNotFoundException` separately from `IOException` lets you distinguish a missing file (expected on first run) from a disk read error (a real problem) without writing two separate try blocks.

> Supports: Exercise 3, which asks you to write explicit exception handlers in `loadFromFile` for four distinct failure modes — missing file, malformed line, IO failure during read, and parse error. Reading the `IOException` subclass hierarchy before writing those handlers ensures that each catch block catches the right exception at the right level of specificity.

### Recommended

**Effective Java, Third Edition — Item 9: Prefer try-with-resources to try-finally** — Joshua Bloch, 2018 | ISBN 978-0-134-68599-1 (available via institutional library)

Bloch's Item 9 addresses the exact resource-management pattern that the chapter gets subtly wrong in its initial code examples: manual calls to `reader.close()` and `writer.close()` that are not guarded by a finally block, or that appear in a finally block without handling the case where both the try body and the close call throw exceptions simultaneously. This scenario — which Bloch demonstrates is the practical outcome of try-finally with two closeable resources — can silently suppress the original exception, making debugging very hard. The item is four pages (pages 40–44 in the third edition); read it before Exercise 4, which asks you to implement the update operation end-to-end. As you work through Exercise 4, refactor your `saveToFile` and `loadFromFile` methods to use the `try (BufferedReader reader = new BufferedReader(...)) { }` syntax Bloch advocates, and note specifically what happens to the `reader.close()` call — it disappears, because the compiler inserts it. I included this because every code sample in the chapter uses manual close, and students who carry that pattern into the project will carry a subtle defect with it.

**The Java Tutorials: The try-with-resources Statement** — Oracle, 2023 | https://docs.oracle.com/javase/tutorial/essential/exceptions/tryResourceClose.html

This short Oracle tutorial page demonstrates the `try-with-resources` statement — the Java 7+ language feature that replaces manual `close()` calls — in about 5–8 minutes of reading. It supports the chapter's exception-handling section directly: the chapter shows you what to catch and how to respond, but its code samples still use manual close, which is the older and more fragile pattern. This page shows the syntax fix in one concrete example and explains what the compiler generates. Read it alongside or immediately after Exercise 3, then compare a try-with-resources version of `loadFromFile` to the version you wrote by hand; pay attention specifically to what happens to the `reader.close()` call and to which exceptions get suppressed vs. propagated in each version. Treat this as a five-minute reference read, not a deep study — skim it once, note the syntax, and use it as a lookup when writing your own persistence methods.

### Further

**Designing Data-Intensive Applications — Chapter 3: Storage and Retrieval** — Martin Kleppmann, 2017 | ISBN 978-1-449-37332-0 (available via institutional library)

This is a professional engineering text written for software engineers building or evaluating production-grade data systems; it assumes comfort with data structures, operating-system concepts, and at least one substantial systems project. Before Chapter 3 pays off, you should already understand why the atomic-rename technique in Module 8 prevents half-written files — specifically, what it means for a filesystem operation to be atomic at the OS level. Without that foundation, Kleppmann's treatment of log-structured merge trees and B-tree indexes will feel disconnected from what you just built. The payoff that the Recommended resources cannot provide is this: Kleppmann explains why the flat-file persistence strategies in this chapter stop working when write throughput or catalog size grows past a certain threshold, what professional storage engines do instead, and what each alternative trades on the exact dimensions the chapter introduces — crash safety, write amplification, and read performance. Chapter 3 (pages 69–99) runs approximately 90 minutes at a careful pace and will give you a durable mental model for why relational databases and key-value stores exist and what they replace. The chapter's "save on exit vs. save after every mutation vs. atomic rename" table is a miniature version of the decision space Kleppmann maps at full professional scale; if you want to understand that space beyond the project requirement, this is the most direct path.
