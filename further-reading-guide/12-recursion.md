# Module 12 — Recursion: Further Reading

> **Content note:** The course outline labels this module "Recursion," but the chapter's actual content covers JavaFX FXML, Scene Builder, the `@FXML` injection mechanism, and the controller lifecycle. The resources below address that actual content.

This chapter explains *how* the `fx:id`-to-`@FXML` injection mechanism works and *why* mismatches produce silent null fields rather than compile errors — but it does not explain the `FXMLLoader` API itself, how to pass data between controllers when navigating between screens, or how JavaFX's application and scene lifecycle governs when injection can safely be used. Closing those gaps lets you build multi-screen flows confidently, not just wire a single screen. The Key resource is worth reading before your Scene Builder redesign lab; the Recommended resources address the two most common extension points the chapter names but leaves open.

Read the Key resource before your lab milestone. Choose one Recommended resource based on whichever gap feels most pressing — pick the Oracle FXML introduction if the injection mechanism still feels uncertain, pick the passing-data tutorial if you need to connect two redesigned screens. The Further item is for students who want to understand the full application lifecycle model; it assumes comfort with the injection mechanism and will take roughly 60–90 minutes.

### Key

**"Introduction to FXML" — OpenJFX Project Documentation, openjfx.io, continuously updated**
This is the authoritative specification for FXML syntax, the `fx:id` attribute, the `fx:controller` attribute, and the injection contract that the chapter depends on. The section "Controllers" (roughly the first third of the document) explains exactly what `FXMLLoader` does when it encounters a `fx:id` attribute: it constructs the component, looks up the matching field in the controller class by name, and calls a `Field.set()` reflective invocation to assign it — which is why a name mismatch leaves the field at its default value of null rather than throwing a compile error. I included this because the chapter correctly describes the behavior but not the mechanism; knowing the mechanism helps you diagnose mismatches without a mapping table to catch them. Read the "Controllers" and "fx:id" sections closely; skim the namespace and include-file sections. Freely available at openjfx.io/javadoc/21/javafx.fxml/javafx/fxml/doc-files/introduction_to_fxml.html.

### Recommended

**"JavaFX: Working with JavaFX UI Components" — Oracle JavaFX Documentation, Oracle Corporation, Java SE / JavaFX 8 and later, continuously updated**
The chapter introduces `TableView` with `PropertyValueFactory` in the `initialize` method but does not explain what `PropertyValueFactory` does or what it requires from the model class. This Oracle guide's "TableView" section explains the cell value factory pattern: `PropertyValueFactory` uses Java reflection to call a getter method on the model object whose name matches the string argument — `new PropertyValueFactory<>("title")` calls `getTitle()` on each `Book` in the table's items list. That means your `Book` class must have a `getTitle()` method (and not just a `title` field) for the table to populate. Read the TableView section in about 20 minutes; it directly explains the populate-table step in your `initialize` method. Freely available at docs.oracle.com/javafx/2/ui_controls/table-view.htm (the cell value factory pattern is stable across JavaFX versions).

**"Passing Parameters Between FXML Documents" — Eden Coding / JavaFX community tutorial, various versions, 2017–present**
The chapter requires you to reconnect the Module 3 two-screen flow after redesigning screens in Scene Builder, but it does not explain how to pass a selected `Book` object from one FXML-controlled screen to another. The standard technique — calling a setter on the destination controller after `FXMLLoader.load()` but before the new scene is shown — is a direct parallel to the Module 3 setter-before-show contract, but the syntax is different because you must retrieve the controller reference from the loader instance rather than from a field. Read any version of this tutorial that covers the `FXMLLoader.getController()` pattern; the Eden Coding version at edencoding.com/pass-data-between-scenes-in-javafx is clear and includes working code. Focus on the section that shows calling a setter on the loaded controller before displaying the scene — this is the mechanism your multi-screen lab flow requires.

### Further

**"JavaFX Architecture" and "JavaFX Application Thread" — OpenJFX Architecture Overview, openjfx.io, continuously updated**
This is specialist-level documentation that describes the threading model underlying the entire JavaFX UI framework, including the Application thread, the pulse system, and the scene graph rendering pipeline. It assumes you are comfortable with the injection mechanism and the controller lifecycle this chapter covers, and that you have some background in concurrent programming or have encountered threading errors in a JavaFX application. The payoff that the Recommended tier does not offer is a principled explanation of *why* all UI mutations must happen on the Application thread and what happens structurally when they do not — which is the root cause of a class of crashes that appear only under load or with background data operations, not in single-user lab testing. After reading this, you can diagnose `IllegalStateException: Not on FX application thread` errors confidently and apply `Platform.runLater()` correctly rather than by trial and error. Expect 60–90 minutes; the architecture overview is at openjfx.io/javadoc/21/. Prerequisite: you should be able to trace the full injection-to-initialize lifecycle from the chapter before this document rewards you.
