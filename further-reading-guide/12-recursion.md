## Further Reading — Module 12: Recursion

> **Content note:** Despite the title "Recursion," this chapter covers JavaFX FXML syntax, the `@FXML` injection mechanism, the `initialize()` lifecycle, Scene Builder as an FXML authoring tool, and the FXML-controller mapping table as a verification discipline. This guide addresses the actual chapter content.

The chapter explains *what* FXML injection does and *why* name mismatches produce silent null fields — but it leaves three consequential questions open: how does `FXMLLoader` actually perform the injection (so you can predict what will break when something goes wrong), how do you hand a model object from one FXML-controlled screen to another in a multi-screen flow, and what does the JavaFX application lifecycle look like when you zoom out from a single controller? These are not academic questions — they are the gaps that stop the Scene Builder lab from working. Understanding them lets you build multi-screen flows with the same confidence the chapter builds for single-screen wiring.

Read the Key resource before your Scene Builder redesign lab. Choose one Recommended resource based on which gap feels most pressing: pick the OpenJFX TableView documentation if the `initialize()` cell-factory wiring is still unclear, pick the inter-controller data-passing resource if your Module 3 two-screen flow needs reconnecting. The Further item is for students who want to understand the threading model that governs when the UI can be mutated safely — it is not required for the lab and is genuinely difficult; set it aside without hesitation if the injection mechanism is still your primary focus.

### Key

**"Introduction to FXML" — OpenJFX Project Documentation, openjfx.io, JavaFX 21 (continuously updated)**
This is the authoritative specification for the FXML language that Scene Builder generates and `FXMLLoader` consumes. I included it because the chapter correctly describes the injection behavior — a name mismatch leaves the field null — but not the mechanism behind it: `FXMLLoader` uses Java reflection to locate a field in the controller class by name and calls `Field.set()` to assign it, which is exactly why a one-character case difference (`bookTable` vs. `BookTable`) produces a null field with no compile error rather than an error you can see before runtime. The "Controllers" section (the first third of the document) covers `fx:controller`, `fx:id`, `@FXML` field injection, event handler wiring, and the `initialize()` contract — the full set of mechanics the mapping table is enforcing. Read the "Controllers" and "fx:id" sections closely before the lab; skim the namespace and include-file sections on first pass. Freely available at https://openjfx.io/javadoc/21/javafx.fxml/javafx/fxml/doc-files/introduction_to_fxml.html.

> Supports: Lab: Scene Builder Redesign — specifically the requirement to complete an FXML-controller mapping table and verify that every `@FXML` field injects successfully; the OpenJFX documentation's explanation of reflective injection tells you precisely what the mapping table enforces and why a name mismatch is invisible at compile time.

### Recommended

**"JavaFX Tutorial — TableView" — Jakob Jenkov, Jenkov.com (JavaFX 21, continuously updated, last reviewed 2024)**
The chapter introduces `TableView` with `PropertyValueFactory` inside `initialize()` but does not explain what `PropertyValueFactory` does or what it requires from the model class. This tutorial's TableView section explains the cell-value-factory pattern: `PropertyValueFactory` uses Java reflection to call a getter whose name matches the string argument, so `new PropertyValueFactory<>("title")` calls `getTitle()` on each `Book` in the table's items list — which means your `Book` class must have a `getTitle()` method, not just a `title` field, for the table to populate. That is a silent failure mode with the same character as an `fx:id` mismatch: the table renders, but it is empty. Read the "TableView Model" and "TableColumn Cell Value Factory" sections (roughly 20 minutes) before writing your `initialize()` method for the redesigned screen; pay specific attention to why `FXCollections.observableArrayList()` is required rather than a plain `ArrayList`. Available at https://jenkov.com/tutorials/javafx/tableview.html.

**"Passing Data Between JavaFX Controllers" — Jakob Jenkov, Jenkov.com (continuously updated, last reviewed 2024)**
The chapter requires reconnecting the Module 3 two-screen flow after redesigning screens in Scene Builder, but it does not explain how to pass a selected `Book` object from one FXML-controlled screen to another. The standard technique — calling a setter on the destination controller after `FXMLLoader.load()` but before the new scene is shown — is a direct parallel to the Module 3 setter-before-show contract, but the syntax differs because you retrieve the controller reference from the loader instance rather than from a field. I included this because the lab's multi-screen requirement is where most students encounter this gap. Read the section covering `FXMLLoader.getController()` and focus on the example that calls a setter on the loaded controller before `stage.show()` — this is the exact mechanism your flow requires. Available at https://jenkov.com/tutorials/javafx/fxml.html; Jakob Jenkov is the primary author of the Jenkov.com Java tutorial series, a well-known independent Java instructional resource.

### Further

**"JavaFX Architecture" — OpenJFX Architecture Overview, openjfx.io, JavaFX 21 (continuously updated)**
This is specialist-level documentation written for developers who have already built functional JavaFX applications and are starting to encounter threading errors or performance issues under real conditions. The entry prerequisite is not general background in concurrent programming — it is specifically the ability to trace the full injection-to-`initialize()` lifecycle from this chapter and recognize what it means for a UI component to be "owned" by the Application thread. Without that foundation, the architecture document's discussion of pulse events and scene-graph rendering will feel abstract. What this gives you that the Recommended tier cannot is a principled explanation of *why* all UI mutations must happen on the JavaFX Application thread — the structural reason that `IllegalStateException: Not on FX application thread` errors appear only under load or with background data operations, not in single-user lab testing. After reading this, you can apply `Platform.runLater()` correctly rather than by trial and error, and diagnose threading crashes by reasoning about thread ownership rather than guessing. Expect 60–90 minutes; available at https://openjfx.io/javadoc/21/ under the Architecture section.
