## Further Reading — Module 6: Basics of GUI Programming in Java

> **Content note:** Despite the title "Basics of GUI Programming in Java," this chapter covers authentication design, password hashing with SHA-256, and threat modeling — not GUI toolkits or JavaFX. This guide addresses the actual chapter content.

This chapter establishes three habits most introductory courses skip: separating domain participants from credentials, hashing passwords before storing them, and writing a threat model before writing any code. What it deliberately leaves open is the distance between that course-project foundation and production-grade practice — specifically, why SHA-256 without salting is insufficient against precomputed attacks, what bcrypt and Argon2 do differently, and how the object-separation principle you practiced connects to the field's broader security vocabulary. That gap is not a footnote; it is where every professional authentication decision lives.

Read the Key resource before submitting the Lab: Account Directory and Login Manager — it directly informs the threat-model table you must produce before writing any code. Choose one Recommended resource based on which concept felt least settled: the Java `MessageDigest` documentation if you want to verify your hash implementation step by step, or the Shostack chapter if you want to understand how the three-row threat-model table scales to professional practice. The Further resource is for students who want the historical origin of the design this chapter teaches — it assumes you are confident in the chapter's core concepts and is entirely optional.

### Key

**OWASP Password Storage Cheat Sheet** — OWASP Foundation, 2024 | https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html

I included this because the chapter names bcrypt, scrypt, and Argon2 as what production systems use but does not explain what they do that SHA-256 does not. This resource fills exactly that gap. The "Background" and "Password Hashing Algorithms" sections — roughly the first third of the page, through the algorithm comparison table — explain salting, adaptive work factors, and why a deliberately slow hash function changes the attacker's cost calculation in ways that matter for your threat-model table. When the chapter asks you to write a row for "what would make the hashed design stronger," this resource provides the specific technical answer: a random salt prevents precomputed lookup tables, and an adaptive work factor makes brute-force attacks computationally expensive regardless of hardware improvements. Read these two sections before completing your threat-model table; skim the rest for awareness.

> Supports: Lab pre-submission requirement — the threat-model table row for "what would make the hashed design stronger" (specifically: salting and adaptive work factors as named technical answers)

### Recommended

**Java SE 21 API Documentation: `java.security.MessageDigest`** — Oracle, 2023 | https://docs.oracle.com/en/java/se/21/docs/api/java.base/java/security/MessageDigest.html

The chapter provides the `hash()` method pattern but does not explain what `getInstance("SHA-256")` is selecting from, why the charset matters, or what happens when `digest()` is called on the same instance twice in a row. The `MessageDigest` class documentation covers the provider architecture, the distinction between one-shot `digest(byte[])` and the update-then-digest workflow, and the thread-safety constraint that makes a shared instance dangerous in concurrent code. This directly supports Exercise 2's step-by-step trace of the `hash()` method: after reading the class-level description and the `getInstance`, `digest`, and `reset` method entries, you should be able to explain every line of the chapter's `hash()` method from the specification rather than from pattern-matching the example. Read the class description and those three method entries; the provider-architecture section is background and can be skimmed.

**"Threat Modeling: Designing for Security"** — Adam Shostack, 2014 (Wiley) | ISBN 978-1-118-80999-0 (available via institutional library)

The chapter introduces the threat-model habit as a three-row table built around a single question: if someone reads my user database, what can they do? Shostack's book is the field reference for that practice at scale, and Chapter 1 ("Dive In and Threat Model!") works through exactly the same framing — attacker perspective, concrete damage, design response — using the STRIDE framework across about 25 pages that are accessible to anyone who has completed this module. I included it because students who want to go beyond the course project's simplified table will find that the professional practice is not more complicated in kind, only more systematic in enumeration. Read Chapter 1 for this module; the "STRIDE per Element" material in Chapter 3 is worth returning to when you reach the authorization module. The book is available through most university library systems and on O'Reilly Safari with institutional access.

### Further

**"Password Security: A Case History"** — Robert Morris and Ken Thompson, *Communications of the ACM*, 1979, Vol. 22, No. 11, pp. 594–597 | https://doi.org/10.1145/359168.359172 (available via ACM Digital Library with institutional access)

This four-page paper is the primary source for the design this chapter teaches: Morris and Thompson describe the original Unix password hashing scheme, explain why storing plaintext was the wrong move even in 1979, and walk through the attacker's problem when facing a hashed credential store — including dictionary attacks and the cost structure that makes weak passwords the binding constraint. It is 46 years old and remains the clearest statement of why one-way hashing is the correct design move and what it does and does not protect against. Written for a systems-programming audience of the era, it assumes comfort with the distinction between plaintext and hashed storage that the chapter establishes — if you cannot confidently explain the chapter's threat-model table from memory, this paper will not yet reward you. What it gives that the Recommended tier cannot is a concrete historical account of the original threat-model reasoning, written by people designing against real attackers: reading it makes the design decisions in this chapter feel necessary rather than arbitrary, and you will notice that every row in your own threat-model table was already anticipated in 1979. Plan for 20 minutes; read it alongside your completed threat-model table and note the correspondence.
