# Module 3 — Objects and Classes: Further Reading

This chapter establishes *why* objects must travel between screens as references and *who* is allowed to modify them — but it does not teach the Java class anatomy needed to build those objects: how to declare fields, write constructors that initialize valid state, or design accessor and mutator methods that enforce ownership rules. Closing that gap lets you implement the setter-before-show contract the chapter requires, not just understand it. These resources also address the two failure modes the chapter names (lost reference, premature display) at a level of mechanical detail the chapter intentionally defers.

Read the Key resource before your lab submission. Choose one Recommended resource based on whichever concept felt least settled after the chapter — pick the Oracle tutorial if you want constructor and field syntax, pick the Bloch excerpt if you want to understand why encapsulation rules matter at design time. The Further item is for students who want to understand the theoretical basis for separation of concerns; it assumes comfort with basic class design and will take roughly 60–90 minutes.

### Key

**"Classes and Objects" — Oracle Java Tutorials (Lesson: Classes and Objects), Oracle Corporation, continuously updated**
The Oracle Java Tutorials "Classes and Objects" lesson covers exactly the Java class anatomy this chapter assumes: declaring fields, writing constructors, defining methods, and using access modifiers to enforce visibility. I included this because the chapter's setter methods (`checkoutPanel.setBook(selectedBook)`) require you to write private fields with public accessor and mutator methods — and the chapter never shows you the syntax for doing that. Work through the "Declaring Classes," "Providing Constructors," and "Returning a Value from a Method" sections; skim the rest. As you read, map each syntax element back to the flow table the chapter asks you to write: your `Book` class needs a field for every cell in that table's "fields read / fields written" columns. Freely available at docs.oracle.com/javase/tutorial/java/javaOO/.

### Recommended

**_Effective Java_, 3rd Edition, Chapter 2 (Items 1–4) and Chapter 4 (Items 15–17)** — Joshua Bloch, 2018
Chapter 2, Items 1–4 cover how objects are created — static factory methods versus constructors — which extends this chapter's treatment of constructors from syntax to design. Chapter 4, Items 15–17 cover minimizing accessibility (why fields should be private and what that decision costs if you get it wrong), which is the theoretical grounding for the ownership rules the chapter enforces by convention. This is the resource that explains *why* the discipline of "decide which screen owns each field" is not just a course rule but a standard professional practice. Read Items 15 and 17 closely; they are short and directly applicable to the Book and Loan classes you will build in the lab. Institutional library access is typically available; the book is also widely held in print.

**"Understanding Instance and Static Members" — Oracle Java Tutorials (Lesson: Classes and Objects, section "Class Members"), Oracle Corporation, continuously updated**
The chapter's topic list includes static variables, constants, and methods, but the prose focuses entirely on instance state. This Oracle section explains the distinction precisely: a static field belongs to the class, not to any instance, so every panel that holds a reference to a `Book` object shares the same static fields but has its own copy of instance fields. That distinction matters directly for the module's lab: if you accidentally declare a `selectedBook` field as static in a panel class, every panel shares the single reference — which appears to work until the second user flow overwrites it. Read this section in about 15 minutes, then ask yourself whether any field in your lab design should be static versus instance. Freely available at docs.oracle.com/javase/tutorial/java/javaOO/classvars.html.

### Further

**_Head First Object-Oriented Analysis and Design_** — Brett McLaughlin, Gary Pollice, and David West, O'Reilly Media, 2006
This is a practitioner-level design book, not a syntax reference; it assumes you are comfortable writing Java classes and want to understand the design principles that govern how responsibilities are divided between them. The chapters on the Single Responsibility Principle and encapsulation (Chapters 1–3) provide the theoretical foundation for the separation-of-concerns model this chapter introduces as the "three-layer responsibility" diagram — visibility to CardLayout, display to panels, state to domain objects. The payoff that the Recommended tier does not offer is a systematic vocabulary for *evaluating* a design: after reading this, you can articulate not just that mixing display and state is wrong, but which design principle it violates and what refactoring pattern corrects it. Prerequisite: you should be able to write a Java class with fields, a constructor, and accessor methods without looking up syntax. Expect 60–90 minutes for Chapters 1–3. Institutional library access is typically available through O'Reilly Learning.
