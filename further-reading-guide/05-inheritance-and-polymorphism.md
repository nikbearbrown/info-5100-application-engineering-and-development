## Further Reading — Module 5: Inheritance and Polymorphism

> **Content note:** Despite the title "Inheritance and Polymorphism," this chapter covers supply-side object modeling — the design practice of separating durable entity and collection classes from the transaction layer that uses them. The assessments reference inheritance and polymorphism topics, but the chapter body teaches the entity/relationship/transaction distinction and catalog preloading. This guide addresses the actual chapter content.

This chapter introduces a design distinction that most introductory courses skip: resources that exist before any user transaction runs versus the transactions that consume them. The question the chapter leaves open is not a settled one — experienced engineers argue about where catalog boundaries should sit, how query responsibilities should be distributed, and when a homegrown collection class needs to become something backed by a database. Three gaps remain after the chapter closes. The chapter assigns an `ArrayList` rewrite as a challenge but never explains `ArrayList`. It introduces the Catalog-as-collection pattern without naming the professional equivalent that will appear in every enterprise codebase. And it names persistence as out of scope without giving you a map toward it.

Read the Key resource before attempting Exercise 7 and before the Graded Lab — it fills a gap the exercise requires. Choose one Recommended resource based on which direction matters most for your project: the Bloch item if you want to understand why professionals avoid raw arrays, the Fowler pattern entry if you are thinking about how your design would extend to a real database. You do not need to read both Recommended resources, and you should skip the Further item until the lab is submitted.

### Key

**The Java Tutorials: Collections Trail — "List Implementations"** — Oracle, continuously updated | https://docs.oracle.com/javase/tutorial/collections/implementations/list.html

I included this because Exercise 7 asks you to rewrite `Catalog.searchByTitle` using `ArrayList<Book>`, and the chapter gives you no foundation for that rewrite. This Oracle tutorial page explains what `ArrayList` is, why it grows dynamically (which eliminates the two-pass sizing problem your current `searchByTitle` has), what the angle-bracket generic syntax means, and how `add`, `get`, and `size` work. The URL above points to the Java SE 21-compatible tutorial. Read the "List Implementations" page with your current `searchByTitle` code open; every sentence about dynamic resizing maps directly to the limitation you are being asked to fix. After reading, you should be able to replace the `Book[]` return type with `ArrayList<Book>` and articulate the trade-off the exercise requires — what the `ArrayList` gives you versus what it costs.

### Recommended

**Effective Java, Third Edition — Item 28: "Prefer lists to arrays"** — Joshua Bloch, 2018 | ISBN 978-0-13-468599-1 (available via institutional library)

I included this because it answers the question your challenge exercise surfaces but does not resolve: why does professional Java code use `List<Book>` instead of `Book[]` even when the size is known at compile time? Bloch explains that arrays and generics have fundamentally different type-checking behavior — arrays are covariant in a way that permits runtime crashes, while generics catch the same errors at compile time. This is not a stylistic preference; it is a correctness argument. Read Item 28 in Chapter 9 after completing Exercise 7. You do not need to follow all of Bloch's type theory — focus on his concrete examples of what fails with arrays and what generics prevent. The section title "Prefer lists to arrays" is stable across the third edition and locates the item reliably without depending on page numbers.

**"Repository" — Martin Fowler, in *Patterns of Enterprise Application Architecture*, 2002, Addison-Wesley** | ISBN 978-0-321-12742-6; pattern summary also at https://martinfowler.com/eaaCatalog/repository.html (stable URL)

I included this because your `Catalog` class is an informal implementation of the Repository pattern — a class that mediates between the domain model and the data source, answers queries, and hides how objects are stored. Fowler names this pattern, describes its intent, and shows how a `findBy*` interface separates the transaction layer from storage concerns. Start with the free online pattern summary at the URL above (five minutes); read the book chapter if you want the fuller treatment. The payoff is immediate: when an interviewer asks how your supply-side design relates to common patterns, "Repository" is the answer, and you will be able to explain why. The book is from 2002, but the Repository pattern has not changed and remains the standard reference.

### Further

**Domain-Driven Design: Tackling Complexity in the Heart of Software — Part II, "The Building Blocks of a Model-Driven Design"** — Eric Evans, 2003, Addison-Wesley | ISBN 978-0-321-12521-7 (available via institutional library)

This is specialist literature written for practicing software architects who have already paid the cost of poor domain modeling in a production system — it is not a student text and will feel dense if you read it before the lab is complete. Before it rewards you, you need to understand what a Repository is (the Fowler resource above covers this) and be able to distinguish between an entity that persists through state changes and a value object defined entirely by its attributes. The two relevant chapters are "A Model Expressed in Software" and "The Life Cycle of a Domain Object" in Part II. Evans formalizes exactly the vocabulary this chapter introduces informally: he distinguishes Entities from Value Objects from Domain Services, names Aggregates as a pattern for managing boundaries around clusters of related entities, and explains why the architectural difference between a `Catalog` holding a raw array and a Repository backed by a database is not a matter of implementation detail but of domain boundary design. The Recommended tier tells you the Repository pattern exists; Evans tells you why it exists, when it should be split into multiple repositories, and what breaks when aggregate boundaries are ignored. That is what this tier gives that the Recommended resources do not — a design vocabulary precise enough to use in professional code review.
